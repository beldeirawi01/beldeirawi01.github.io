SauceDemo framework with CI/CD

View the repository
S

Situation

UI regression checks that break whenever the interface changes slow a team down and get ignored. I built this framework to avoid that, using SauceDemo as a realistic storefront.

T

Task

Design a maintainable end-to-end framework that covers the full purchase journey, runs on every change and stays stable across browsers.

A

Action

Built a Page Object Model in Playwright and TypeScript with assertions kept in the specs, data-test locators, custom fixtures for a logged-in session and data files for edge cases. Replaced one-time reads like page.url() and .count() with auto-retrying assertions after they proved flaky across browsers. Tagged tests @smoke or @regression, wrote a test plan, and documented known defects as test.fail() tests so the suite stays green and flags the day one is fixed.

R

Result

63 tests running as 167 executions on every push and pull request. The latest run passed 167 of 167 with 0 flaky tests in 4.2 minutes, and a UI change is fixed in one page object.

API testing: contracts, auth and tenant isolation

View the API tests
S

Situation

Offices-App’s Express API handles invoices, payments and data for many separate businesses, so a wrong response or a leaked record is costly. I also tested a public booking API, Restful-booker, a shared service that resets itself on a timer.

T

Task

Verify API contracts, authentication rules and data isolation against real behavior, and make those checks run automatically on every change.

A

Action

Wrote Vitest and Supertest integration tests against a real PostgreSQL database, not mocks, covering auth, cross-tenant isolation, invoice send and void guards and the voice-extraction invoice logic. Built a Playwright API suite for Restful-booker covering authentication, booking CRUD and negative cases such as a request without a token. Each test creates its own data, and update and delete tests read the booking back to prove the change happened.

R

Result

Tenant isolation and invoice rules are regression-tested on a fresh Postgres container in CI on every backend change. The API suite surfaced two real defects, a 200 on bad credentials and a 500 on a missing required field, now documented as test.fail() tests.

T

A
